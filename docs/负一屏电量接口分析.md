# 负一屏"随身设备电量"接口设计分析与实现方案

> 任务:把 BLE 电池(迪子电量 / FD 前缀 BMS)的电量,"像随身设备(耳机/手表)的电量一样"注册显示在鸿蒙 NEXT 的负一屏;若接口需要持续提供最新数据,则在断联后锁定最后电量,不让它离线消失。

## 一、负一屏电量显示的官方"接口"到底是怎么设计的

通过华为消费者官网与开发者联盟文档(2025-2026 版本)调研,负一屏(智慧助手·今天)与电量相关的能力有 **三套完全不同的接口**,设计如下:

### 1. 系统级"设备电量"服务动态卡片(耳机/手表看到的那种)

- 官方说明:《智慧助手·今天(负一屏)设备电量服务动态卡片介绍》(consumer.huawei.com zh-cn16017262)。
- 数据来源:**系统蓝牙协议栈**。手机自己、反向快充对端、通过蓝牙/星闪连接的华为耳机、WATCH、手环、眼镜、手写笔等,由系统在建立连接时通过蓝牙标准电量通道(HFP 电池指示 / GATT Battery Service 0x180F 等厂商私有约定)读取电量,写入系统设备数据库。
- 触发条件:设备必须与手机建立**系统层蓝牙连接**;穿戴设备还要求运动健康 App 已授权。
- **开放程度:不开放**。这是"系统服务"卡片,文档明确标注为"系统服务",没有任何面向第三方应用的写入/注册 API。第三方应用无法把一个自定义 BLE 设备的电量"注册"进去。
- 我们的电池 BMS 只暴露 Nordic UART (NUS) 透传服务,**没有标准电量服务**,即使系统连上也读不到电量。修改固件加 GATT Battery Service(0x180F/0x2A19)是让系统卡片原生显示的唯一"正规"路径,但这需要改电池固件,不在应用侧能力范围内。

**结论:此路不通,无接口。** 这就是"看一下这个接口是怎么设计的"的第一层答案:它是系统闭环设计,没有第三方注册接口。

### 2. 负一屏"服务动态"(动态卡片流)

- 开发者入口:智慧助手·今天(服务分发)→"服务动态接入"(developer.huawei.com/cn/doc/atomic-guides/push-as-timeline)。
- 接口设计:**Push Kit 服务时序消息(实时活动)**。第三方以**元服务**身份接入,由**服务端**通过华为 Push 随时更新卡片内容(快递轨迹、订单状态等),卡片出现在负一屏搜索框下方的"服务动态"模块(就是系统电量卡片所在的模块)。
- 关键设计特征:
  1. **数据必须由服务端持续推送**(push 驱动,无推送则卡片保持/过期);
  2. 仅限元服务 + AGC 审核开通,场景限定"履约过程"(订单/物流/出行等);
  3. 完全依赖云侧,本地 BLE 设备离线时无法提供数据。
- 对本任务:不适用(需要 AGC 企业资质 + 服务器 + 履约场景,且恰恰违背"离线后仍要显示"的需求)。

**结论:这是唯一能进入"系统电量卡片同模块"的第三方通道,但它是云推送接口,不是设备注册接口。**

### 3. 负一屏"卡片"专区 + 桌面服务卡片(Form Kit)——本方案采用

- 官方说明:《智慧助手·今天(负一屏)"卡片"专区介绍》(zh-cn16038618)。
- 接口设计:HarmonyOS 5.0.0.135 SP1+ 且"智慧助手·今天" ≥15.0.12.300 后,负一屏新增"卡片"专区,用户可把**服务卡片(FormExtensionAbility 提供的 ArkTS 卡片)**常驻添加到负一屏(也可添加到桌面);最多 20 张,可置顶。
- 添加途径:负一屏卡片市场(榜单)/ 元服务右上角"卡片"→"添加至负一屏"。元服务可直接添加;普通应用的卡片需经 AGC"服务直达"上架卡片市场。
- 更新接口:`formProvider.updateForm(formId, data)` 应用随时可推;卡片配置里 `updateEnabled + updateDuration`(最短 30 分钟定时兜底)+ `scheduledUpdateTime` 定时刷新。
- **这是完全开放给第三方应用的本地接口**,不需要服务器。

**结论:用 Form Kit 服务卡片承载"电池电量"显示,样式仿照随身设备电量;卡片可加到桌面,在支持的系统版本上加到负一屏卡片专区(上架 AGC 卡片市场后可在卡片市场出现)。**

## 二、"断联后锁住电量"的设计(按用户要求的降级策略)

官方没有"外部设备电量注册"接口,因此不存在官方的"离线判定"逻辑需要绕过;真正需要设计的是**卡片数据生命周期**。本项目实现为:

```
                    ┌──────────────────────────────┐
   BLE 广播(~1s/条)─▶│ BatteryMonitor (长时任务)      │
   GATT 完整读取(5s) │  解析 → BatterySnapshot 快照   │
                    └──────────────┬───────────────┘
                                   │ 每次数据变化
                                   ▼
                     preferences 持久化快照(最后已知电量)
                                   │
                    formProvider.updateForm(所有已添加卡片)
```

1. **快照永不清空**:应用内 `BatterySnapshot` 持久化到 preferences(进程被杀、重启后仍在)。任何渲染路径(应用 UI、卡片 onAddForm/onUpdateForm/onFormEvent)都只从"最后已知快照"取数,**代码里不存在"离线/清空"分支**。
2. **锁住判定**:距最后数据 >10 分钟 → `locked=true`。UI 仅显示一个"电量已锁定"小徽标和最后更新时间,**电量数值本身永远保持最后已知值继续显示**——不会出现"离线"、不会清零、卡片不会消失。
3. **持续供数**(有信号时):
   - 广播通道:FD 电池每秒广播 SN+电压+电量,**无需连接**即可刷新卡片;
   - 连接通道:长时任务(bluetoothInteraction)内维持 GATT 连接,5s 轮询 F403 读 124 字节 BMS 寄存器,获得电流/功率/温度/15 串电芯/循环/SOH;
   - 断联后自动重连(可关),重连成功即恢复实时。
4. **兜底刷新**:卡片 `updateDuration=1`(30 分钟)定时用持久化快照重绘,保证极端情况(应用被杀)后卡片仍在且数值是最后的锁定值。点击卡片拉起应用恢复监控。
5. **后台保真说明**(平台限制,如实记录):第三方应用的持续 BLE 扫描/连接依赖长时任务;用户从最近任务划掉应用后系统会取消长时任务,此时卡片继续显示锁定电量,打开应用即恢复实时。要达到"永不停止"必须系统级签名,应用侧无法突破。

## 三、结论对照用户需求

| 需求 | 结论 |
|---|---|
| 像随身设备一样注册到系统电量卡片 | 官方无第三方注册接口(系统闭环),改用负一屏卡片专区/桌面服务卡片,样式与信息密度对齐"随身设备电量"卡片 |
| 看接口是否需要持续提供最新数据 | 服务动态(与系统电量卡片同模块的第三方通道)是云推送驱动、需持续供数;服务卡片则是应用推数 + 定时兜底 |
| 断联后锁住电量、不让它离线 | 已实现:持久化最后快照 + 永不清空 + 锁定徽标 + 30 分钟兜底重绘 + 自动重连 |
